# 14. 项目匹配规则配置化（2026-08-15）

> 主题：编号 → 检验项目类型的匹配规则从代码常量迁移为 DB 规则实体，
> 管理员在流程管理中实时编辑、保存即生效；为第 2 步（共性节点参数化）
> 与第 3 步（设计器表单化/代码节点）落定数据形状。

## 背景与触发

- 共享盘目录结构明年可能变化；项目名/标准号/单元格坐标此前硬编码在
  `paper_fiber.py`、`microscopy_families.py`、`regenerated_fiber.py`。
- 流程定义 JSON 走草稿→发布，不满足"实时更新"；因此规则独立存表，
  节点 config 以 `match_rule: <rule_key>` 引用。

## 机制总览（规则化后）

匹配仍依赖两条数据源，均不因规则编辑而重建：

1. 共享盘文件索引（`execution_file_index_entries`，后台扫描）；
2. 旧系统任务单快照缓存（`execution_task_snapshot_cache`，只读 Bridge
   回填的原始事实）。

汇合层 `catalog_recommendations` 按特化节点类型分派到三个匹配器；
匹配器从规则表读取全部"发现期事实"：root_id、目录策略、任务单事实
（项目名别名/测试方法）、结果探针（sheet/cell/parser）。命中条件打分
排序语义不变。

## 规则表 `execution_project_rules`（迁移 0007）

列：rule_key（唯一）、display_name、category_key、enabled、revision
（每次保存 +1）、config（JSONB）、updated_by_id、时间戳。

config 结构：

```json
{
  "default_node_type": "file.paper_fiber_gbt4688_qualitative",
  "record_family": "microscopy",
  "source": {"root_id": "...", "folder_match": {
    "strategy": "level1_contains_number | filename_contains_number | electron_image_folders",
    "entry_kind": "workbook | image", "max_depth": 2}},
  "task_facts": [
    {"condition_key": "task_item_name", "fact": "check_item_name",
     "op": "in", "values": ["别名1", "别名2"]},
    {"condition_key": "test_method", "fact": "check_method",
     "op": "eq", "values": ["GB/T 4688-2020"]}],
  "probes": [{"name": "qualitative_result", "type": "cell_value",
    "sheet": "Sheet1", "cell": "W32", "parser": "paper_qualitative_v1"}],
  "binding": {"family_key": "microscopy", "check_item_no": "5103.5",
    "check_item_name": "纤维微观形貌"}
}
```

- 比较语义：NFKC + 空白折叠（与此前硬编码一致）。
- `binding` 仅电镜两条规则有：把规则链接到代码钉死的模板绑定族，
  并承载写门禁反查用的规范项目编号+名称。
- 种子五条（`project_rule_seeds.py`，代码常量仍是唯一种子事实源）：
  `paper_gbt4688_qualitative`、`microscopy_gbt36422_microscopy`、
  `microscopy_gbt36422_cross_section`、`regenerated_fiber_count_method`、
  `regenerated_fiber_area_method`。`ensure_default_project_rules` 只补缺、
  不覆盖管理员修改；迁移只建表，播种由运行时幂等完成。

## 运行时接线

- 三个匹配器签名增加 `rule_key` / `rule`（已解析规则优先）；目录推荐
  按节点 config 的 `match_rule` 覆盖默认映射（`default_rule_key_for_node_type`）。
- 停用规则：目录显示 `rule_disabled` 且不可运行；节点执行 422
  `project_rule_disabled`。
- profile 缓存（纸类 W32、再生纤工作表）有效性键加入 `rule_revision`：
  保存规则即自动失效重读，无需清表；revision 不变则照常命中。
- 新通用节点 `core.project_match`（registry 注册，executor =
  `evaluate_project_rule` 按 `default_node_type` 分派），第 2 步的
  "通用匹配节点"即是它；四个特化节点 config_schema 增加
  `match_rule`（`x-param-type: project_rule_ref`，第 3 步设计器表单化
  的元数据通道）。
- 节点输出钉 `rule_key` + `rule_revision`（运行期审计/重放基础）。
- 写门禁：电镜 `microscopy_family_for_project(..., db=...)` 经
  `rule_for_facts` 按 binding 编号+名称反查（查不到 fail closed）；
  纸类 `_validated_paper_project_binding` 接受规则驱动的项目名/方法。
  **写入契约常量不动**：`ELECTRON_TEST_METHOD`、纸类上传头校验、模板
  绑定 SHA256 仍代码钉死——规则管"发现/匹配"，代码管"写入能力"。

## API 与界面

- `GET/PUT /project-rules[/{key}]`、`POST /project-rules/test`
  （干跑不落库，支持 rule_key 或临时 config）；PUT 校验配置、核对
  root_id 存在、revision+1、写审计日志（含旧 config）。
- 流程管理列表行："匹配规则"按钮（`match_rule` 摘要由后端随流程列表
  下发）+ 名称行规则摘要；设计器节点面板：`match_rule` 参数渲染为
  规则下拉 + "编辑规则"按钮。
- 编辑抽屉：展示名/启用/root_id/目录策略/别名/测试方法/binding/探针
  表格 + 编号干跑测试；保存即生效（推荐列表按请求实时计算）。

## 明确不做（本步边界）

- 外部操作 payload 不钉 rule revision：`request_summary` 参与幂等
  checksum，钉入会在规则编辑后造成伪幂等冲突；审计以节点输出为准。
- `full_match_requires` 不进配置（四个条件即流程身份，无编辑需求）。
- 存储根 base_path 不开放在线编辑（env/DB 层；规则引用 root_id 已解耦
  路径变更）。
- 模板绑定/Writer 白名单永不配置化。

## 1. 这个目录解决什么问题

这里用于把每轮讨论中的零碎想法，逐步整理为可以验证、可以决策、以后可以转成产品需求和技术设计的结构化资料。

本阶段不追求一次性“写死完整方案”，而是持续完成以下循环：

1. 记录事实、案例和用户原话；
2. 区分已确认需求、暂定建议和待确认问题；
3. 补充流程、节点、数据、交互和系统边界；
4. 发现冲突时修正文档，而不是并列保留互相矛盾的方案；
5. 每次修改同步记录在 `CHANGELOG.md`；
6. 达到足够确定性后，再形成正式 PRD、原型和开发任务。

## 3. 统一标记

- **[不在当前阶段]**：明确暂缓开发或集成。

## 4. 当前最重要的结论

1. 这不是单一的 Excel 自动化工具，而是一个面向检测业务的**人机协同、可暂停恢复、可审计的执行系统**。
2. 工作流编辑器和检验员实际使用的执行界面必须分开：管理员设计流程，检验员看到的是简洁的任务工作台。
3. 人工输入不应依赖临时弹窗，而应建模为可持久化的“人工任务”，允许离开页面后继续处理。
4. 所有节点都需要明确、可校验的输入输出契约；文件应以“文件对象/制品”流转，而不是传递任意绝对路径。
5. 原始文件默认只读，Excel 合并采用副本写入和预检查，不能直接破坏原记录。
6. 执行内核采用面向检测业务的自有模型；Dify 仅作交互参考，不 Fork，Graphon 不作为首版核心。
7. 首版同时提供完整流程设计器和“找文件—选择—人工确认”的可运行流程；受控 `.xlsx` 写入用隐藏测试流程验收，暂不直接提交检务系统。
8. 执行系统已使用 30 张领域表持久化定义、运行、人工任务、制品、审计和
   Worker 心跳；API 存活与业务就绪采用不同端点。
9. 发布是不可忽略的副作用：失败或取消发生在发布期间时，运行先进入
   `failure_pending` 或 `cancel_pending`，待回执/对账信息持久化后才能进入
   最终状态。
10. 当前真实样本索引及首笔 FibreCheck 官方 DAL 写入已跑通；外部检务
    连接器接口、PostgreSQL 全局容量门禁和管理员人工对账闭环已经存在。
    当前对账材料明确属于 `admin_attestation_v1` 人工声明，不是系统签名的机器
    探针结果；故障测试、只读观察产物绑定和凭据 ACL 完成前仍保持总开关禁用。
11. 迁移门禁已经在真实 PostgreSQL 上覆盖“空库升级”和“既有库严格结构预检
    后 stamp”；前后端及独立 Worker 镜像也已完成不构建 Area Infer 的容器验收。
12. 当前 Docker 构建仍报告既有前端依赖中的安全告警；在上线前需要单独完成
    生产依赖审计和兼容性升级，不能把离线审计结果视为已消除风险。
13. 工作流版本和每次运行都固化能力快照与契约校验和；公共写入 API 不能绕过
    实际执行路径、人工确认或发布节点，发布栅栏先于物理文件副作用提交。
14. 三类执行目录在应用、Worker 和部署预检中均要求彼此独立、不可父子嵌套或
    通过符号链接指向同一位置，避免源资料被误当成 staging/publish。
15. 电镜流程已采用“后台递归索引 + PostgreSQL 任务快照缓存 + 独立 Windows
    只读 Bridge”；`26A029794` 已完成选图链路，`260061860` 已用真实共享盘图片
    生成并重读核对 `.xls`；单图及 2/5/10 图已通过真实 Windows Excel 比例验收。
16. 图片类旧系统上传和特纤复核已有独立持久化协议、精确项目绑定和只读
    dry-run，但远端权限、唯一性和文件服务器事实尚未实机证明，因此三层保持禁写。

# Windows Bridge 1.3.1：异常保留与自动恢复

## 已确认的现场问题

- 生产纸浆运行 `b62f0060-c2a9-42c2-b16b-a9d0b357b3d5`（`26W007577`）的上传操作已排队，尚未被 Windows Bridge 领取。
- 阻塞来自上一条 `260903369` 的 Excel 登记尝试 `f9123c1c-c5f6-4894-ba05-c30494922cdc`。Writer 在 Excel 采集阶段失败，服务器记录 `excel_write_failed_COMException`，旧版桥将本地 pending 作为全局停止条件。
- 该子运行 `2b42c2cc-b169-4042-a2d9-ec9b5f8f4fe1` 及父运行 `168e5204-02bd-4a73-b300-2d654c048136` 已请求取消，但仍停在 `cancel_pending`。
- 只读检务查询确认横截面项目登记数量仍为 1；本次失败未进入登记保存阶段。旧 Writer 丢弃了异常消息和堆栈，无法从现有回执还原具体 Excel COM 原因。

## 修复行为

- Writer 保留异常类型、完整消息、HRESULT、堆栈及内层异常；已知密码值不进入诊断。Bridge、API 和运行详情均保留结构化异常，支持展开及复制。
- 一条失败操作由服务端接管后，Bridge 继续处理其他编号。成功回执也先落盘，断网重连只重报回执，不重新执行 Writer。
- 新安装器可直接覆盖留有 pending 的 1.3.0；实际仍在运行的 Writer 正常收尾后再替换程序。旧 pending 自动回报，随后恢复接单。
- Writer 明确退出后，已请求取消的运行可以结束；未知远端结果仍留在原操作中，不伪造成功，也不自动重复提交。
- 同一新版 Worker 可以继续处理本次生产旧快照中合同未变的节点。已发布流程在容器启动时自动更新实现依赖，保留本地业务内容、目录和凭据绑定、未发布草稿及启停状态。
- v2 通用外部操作也显示运行页的“旧系统上传”入口，不再因节点名称不是 `external.legacy_*` 而隐藏。
